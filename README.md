# lean-assembly-compiler

Machine code proved correct against Sail-generated CPU models in Lean 4. Work in progress.

## What is kernel-checked today (RISC-V, Sail model `opencompl/sail-riscv-lean`, unmodified)

Source language (`Proven/Code.lean`): `Exp` over four 64-bit inputs (`a0..a3`), 64-bit constants, and
- `bin op a b` with `op` one of `add sub and or xor` and
  - `shl / lshr / ashr`: shift by `b.toNat % 64` (`a <<< (b.toNat % 64)`, `a >>> ..`, `a.sshiftRight ..`),
  - `ult / slt`: `if a < b then 1 else 0` (unsigned) / `if a.slt b then 1 else 0` (signed),
  - `eq`: `if a = b then 1 else 0`;
- `ite c a b`: `if c = 0 then b else a` (branch-free: both arms are evaluated).

RV64I code (base ISA only): R-type `add sub and or xor sll srl sra slt sltu`, `sltiu t,t,1` (for `eq`),
`sltu t,x0,t; sub t,x0,t` + `xor/and/xor` mask arithmetic (for `ite`), over 11 temporaries `t0..t6, a4..a7`.

- `Proven.compile_ok` (`Proven/Compiler.lean`): for every `e : Exp` with `e.depth < 11`, the code `compile e`
  placed anywhere in RAM runs on the Sail model with no trap and no model error, returns to `ra`, leaves
  `a0 = e.denote (a0, a1, a2, a3)`, leaves memory unchanged, keeps callee-saved registers and the control state `Cfg`.
  (`depth` counts the extra temporaries needed: `bin`: `max a.depth (b.depth + 1)`, `ite`:
  `max c.depth (max (a.depth + 1) (b.depth + 2))`; there is no spilling, so deeper expressions are rejected.)
- Per-instruction step lemmas for every emitted word: `Proven/Words.lean`, generated by `Proven/gen_words.py`
  (one `step_word` proof per concrete word, ~215 lemmas, ~6 min to build).
- `Proven.demo_ok`, `Proven.demo2_ok` (`Proven/Reify.lean`): the same for Lean functions `demo` / `demo2`,
  reified by `reify%` (which accepts `+ - &&& ||| ^^^`, the shift forms above, `if a < b then 1 else 0`,
  `if a.slt b then 1 else 0`, `if a = b then 1 else 0`, `if c = 0 then y else x`, and closed constants);
  `demo2` uses every new operator.
- Axioms used (from `#print axioms compile_ok`): `propext`, `Classical.choice`, `Quot.sound`, plus axioms declared by
  the generated model: `cancel_reservation`, `get_16_random_bits`, `load_reservation`, `match_reservation`,
  `plat_term_write`, `sys_enable_experimental_extensions`, `valid_reservation`, and the 67 softfloat externs
  `riscv_f16Add` ... `riscv_ui64ToF64` from `LeanRV64D/RiscvExtras.lean` (they enter through `try_step` in
  `Proven/Step.lean`, already before the operators above were added; no float instruction is executed). No `sorryAx`.

### Loops (RISC-V; `Proven/Branch*.lean`, `Proven/Loop*.lean`)

- Branch/jump step lemmas with a **symbolic** offset (`Proven/Branch.lean`, generated `Proven/BranchWords.lean` by
  `Proven/gen_branch.py`): `b<op> rs1, rs2, 2*o` for `op ∈ beq bne blt bge bltu bgeu`, `rs1 ∈ {t0,t1,a0..a3}`,
  `rs2 ∈ {x0,t0,t1}` (84 instances; `bltu/bgeu` with `x0` omitted), any `o : BitVec 12`, and `jal x0, 2*o` for any
  `o : BitVec 20`. Each: one retired step, `PC = if bcond op x[rs1] x[rs2] then pc + signExtend(o++0) else pc + 4`
  (`step_<op>_<rs1>_<rs2>`, `step_jal_0`), registers and memory unchanged (`jal` writes `rd = x0`), `Cfg` kept.
  The model has C (`misa` bit 2) enabled, so `jump_to` only requires target bit 0 = 0 (2-alignment); our offsets
  are multiples of 4 (`boff_fwd`, `joff_back`). The decoder is run on `c ||| imm o` with bit-range lemmas
  (`B_known`/`B_mismatch`/`B_imm`); all bit-level side lemmas are proved by kernel-checked bit enumeration
  (`bits`), not `bv_decide`.
- `runsTo` rules (`Proven/LoopRule.lean`): `runsTo_mono`, `runsTo_trans`, and the loop rule `runsTo_loop`
  (invariant + `Nat` measure; `runsTo_while` with explicit head/exit PCs).
- `Proven.compileS_ok` (`Proven/Loop.lean`): source `Stmt` = `assign (v : Fin 4) (e : Exp) | seq | loop c body`
  (`while c ≠ 0`), variables `a0..a3` (`gen` never uses them as temporaries), big-step semantics `Exec`
  (`Exec.loop_of`: loops via a user-supplied measure). If `Exec p σ σ'` and `p.wf` (expression depth < 11, each loop
  fits the `beq` range), the code `compileS p` (expressions by `gen`, `beq t0,x0` exit, `jal x0` back edge) placed
  anywhere in RAM runs to its end with `a0..a3 = σ'`, memory unchanged, callee-saved registers and `Cfg` kept.
  `compileF_ok`: same for `compileF p = compileS p ++ [ret]`, returning to `ra`.
- `Proven.sum_ok`, `Proven.gcd_ok` (`Proven/LoopExamples.lean`): the ordinary Lean functions
  `sumDown n acc = if n = 0 then acc else sumDown (n-1) (acc+n)` and
  `gcdSub a b = if a = 0 then b else if b = 0 then a else if a < b then gcdSub a (b-a) else gcdSub (a-b) b`
  (well-founded recursion), `Stmt` programs `sumProg`, `gcdProg`, proofs `sumProg_exec`/`gcdProg_exec` that they
  compute them (`Exec.det`: the result is unique), and the machine theorems (`a0 := f a0 a1`, return to `ra`).
- Axioms: the same list as `compile_ok` above (no `sorryAx`, no `bv_decide`/`native_decide` axioms).
- Check times: `BranchWords` ~7 min (one `bstep` per lemma, ~1.6 s), `Branch` 7 s, `Loop` 7.5 s,
  `LoopExamples` 1.2 s, `LoopRule` 0.7 s. Build with `lake build Proven.LoopExamples`.

## Memory (RISC-V, kernel-checked unless marked)

- Memory model (`Proven/MemModel.lean`, no Sail): a `Block` is a list of byte addresses (cell `i` = logical
  byte `i`), a `Layout` is the list of blocks in use (no allocator); `Layout.ok` = every cell in RAM, no
  block repeats a cell, blocks pairwise share no cell. `bytesOf s b` reads a block in logical order.
  `layout_write`: writing cell `i` of block `L[k]` changes `bytesOf L[k]` at index `i` only, keeps every other
  block of an ok layout and every address outside `L[k]`; `layout_writeAll`: the same for writing all cells
  (`writeCells`). Contiguous `Region`s are an instance: `Region.cells r = List.range' r.base r.len`,
  `bytesAt_eq : bytesAt s a n = bytesOf s (Region.cells ⟨a, n⟩)`, `disjoint.cells`, `Layout.ok_regions`.
- Step lemmas (`Proven/MemWords.lean`, generated by `Proven/gen_mem.py`, ~23 min; `Proven/MemSteps.lean`):
  `lbu rd, 0(rs1)`, `ld rd, 0(rs1)`, `sb rs2, 0(rs1)`, `sd rs2, 0(rs1)` for `rd/rs2 ∈ t0..t6, a4..a7`,
  `rs1 ∈ s1, a0..a3` (220 per-word lemmas against the Sail model + family lemmas `step_lbu/ld/sb/sd`):
  one retired step to `pc + 4`, `Cfg` kept, address in RAM (`0x80000000 ≤ a ∧ a + n ≤ 0x100000000`),
  `ld/sd` 8-aligned. `sb`: `s'.mem = s.mem.insert a (x[rs2].setWidth 8)`; `sd`:
  `s'.mem = storeBytes s.mem a (le8 x[rs2])` (little-endian); `lbu`: `x[rd] = b.setWidth 64` if `s.mem[a]? = some b`;
  `ld`: `x[rd] = v` if `bytesAt s a 8 = (le8 v).map some`. Layout/region forms: `Next.store_cell`,
  `Next.store_block8`, `Next.store_region`, `Next.store_region8`.
- `Proven.compileStore_ok` / `Proven.compileStore_regions` (`Proven/MemCompiler.lean`): `compileStore e =
  gen e 0 ++ [sd t0, 0(s1), ret]` (the existing `gen`, reused through `gen_ok`). The output pointer is in `s1`
  (x9): every other caller-saved register except the inputs `a0..a3` is a temporary of `gen`, and `gen_ok` only
  guarantees that non-temporaries are kept. For `e.depth < 11`, `Cfg`, code at `pc`, even `ra`, output block
  `L[k] = [s1, s1 + 8)` of an ok layout `L` (resp. region `rs[k] = ⟨s1, 8⟩` of a list of in-RAM pairwise
  disjoint regions), `s1` 8-aligned, code not overlapping the output: the Sail model runs to `ra` with
  `bytesAt s' s1 8 = (le8 (e.denote (a0, a1, a2, a3))).map some`, every other block/region unchanged, every
  address outside the output unchanged (`unchangedOutside s s' [rs[k]]`), callee-saved registers and `Cfg` kept.
  Axioms: the same list as `compile_ok`. Check times: `MemModel` 1.2 s, `MemStep` 1.4 s, `MemWords` ~23 min
  (220 lemmas, ~6 s each), `MemSteps` 1.9 s, `MemCompiler` 1.5 s (each including imports).
- Tested: `asm/memtest.py asm/memtest-data/memtest.txt` (input from `asm/memtest-data/memtest.lean`): 5
  expressions x 99 inputs, the code called with `s1` = 16-byte slots pre-filled with `0x55`: Lean `Exp.denote` ==
  8 bytes stored on QEMU == on the Sail C emulator, the guard bytes after each slot intact, and the Sail
  emulator's only data writes are the 8-byte stores to the slots.
- Why `Proven/SortSteps.lean`'s load/store lemmas failed with `(kernel) deep recursion detected`:
  `step_word` unfolds `range_subset` (the PMA range check) on the symbolic data address; `simp` with
  `BitVec.toNat_sub` turns it into `(18446744071562067968 + x.toNat) % 2^64 ≤ 2147483648`, partly through
  definitional (`rfl`-lemma) steps whose kernel check unfolds `BitVec` subtraction with 64-bit literals.
  Located with `Proven/MemDebug.lean` (`kfind tac`: re-checks every subterm of the proof with the kernel and
  reports the minimal failing ones). Fix (`Proven/MemStep.lean`, `mem_word`): `range_subset` stays folded and
  is rewritten by the existing `in_ram` lemma; `split_on_page_boundary` is replaced by summaries
  (`page1`, `page8`). Each load/store lemma then checks in ~6 s.

### Byte arrays: loops + memory (RISC-V; `Proven/Arr*.lean`)

- Source (`Proven/ArrCode.lean`): `AExp` = `Exp` over 8 variables `v0..v7` (= `a0..a7`); `AStmt` = `assign v e`,
  `load v b i` (`v := zero-extended byte i of block b`), `store b i e` (`byte i of block b := low byte of e`), `seq`,
  `loop c body`. State `AState` = variables + `heap : List (List (BitVec 8))` (block contents). Big-step `AExec`:
  an out-of-bounds load/store has no derivation, so a terminating `AExec` run is memory safe.
- Compiler `compileA bv` (`Proven/Arr.lean`): block `b`'s base address is in variable `bv[b]`; address
  `bv[b] + i` is computed by `gen8` into `t0`, then `lbu t0, 0(t0)` / value into `t1` and `sb t1, 0(t0)`.
  Temporaries `t0..t6` (expression depth < 7). New per-word lemmas (`Proven/ArrWords.lean`, generated by
  `Proven/gen_arr.py`, 56 s): `add t_k, x0, a4..a7`, `add a4..a7, x0, t0`, `lbu t0, 0(t0)`, `sb t1, 0(t0)`.
- `Proven.compileA_ok` / `Proven.compileAF_ok`: if `AExec p σ σ'`, `p.wf bv` (depth bounds, base variables never
  assigned, loop bodies within the `beq` range), the data regions `R` are in RAM and pairwise disjoint, the code
  region is disjoint from all of them, and the machine state represents `σ` (`Rel bv R σ s`: `a_i = σ.env i`,
  `bytesAt s R[b].base R[b].len = σ.heap[b]`, `a_(bv[b]) = R[b].base`), then the Sail model runs to the end of the
  code (resp. returns to `ra`) in a state representing `σ'`, with memory outside `R` unchanged, callee-saved
  registers and `Cfg` kept. (`gen8_ok` in `Proven/ArrExp.lean` is `gen_ok` re-proved for 8 variables.)
- End-to-end examples (`Proven/ArrExamples.lean`): `sumCode_ok` (`a2 = sumBytes xs`,
  `sumBytes xs = xs.foldl (· + ·.setWidth 64) 0`, memory unchanged), `takeCode_ok` (output block of
  `min n |xs|` bytes `= xs.take n`, input and all memory outside the output block unchanged), `incCode_ok`
  (`(xs.take n).map (· + 1)`); generic `mapCode_ok`. Axioms: the same list as `compile_ok`.
- Check times: `ArrWords` 56 s, `ArrExp` 1.3 s, `Arr` 2.4 s, `ArrExamples` 1.4 s.
- Tested: `asm/arr_test.py {sum,take,inc} 200` (words from `asm/emit_arr.lean`): 200 random inputs each
  (lengths 0..64, n up to 2^64-1), QEMU == Sail C emulator == Python model on the output slot and its 0x55 guard
  bytes, input unchanged, every Sail data write inside the expected output bytes.

### Sort (RISC-V; `Proven/SortIns.lean`, `Proven/SortMachine.lean`)

- `sortProg` (an `AStmt`): copy input to output (`mapProg`), then insertion sort in place on the output block
  (nested loops; the inner loop is branch-free: `out[j] := c ? out[j-1] : key`, `j := j - c`).
- Source level: `sortProg_exec`: the output block ends as a permutation of the input that is sorted
  (`List.Pairwise (· ≤ ·)`); `sortProg_mergeSort`: it equals `xs.mergeSort leB` (`leB a b = decide (a ≤ b)`),
  by uniqueness of sorted permutations (`List.Perm.eq_of_pairwise` from core, antisymmetry of `≤` on `BitVec 8`).
- `Proven.sortCode_ok` (`sortCode = compileAF [0, 3] sortProg`, 104 words): input `xs` at `a0` (length `a1`), output
  block of `|xs|` bytes at `a3`: returns to `ra` with the output block `= xs.mergeSort leB`, input unchanged, all
  memory outside the output block unchanged, callee-saved registers and `Cfg` kept.
- `Proven.sortCode_implements : ImplementsMapped sortCode (fun x => x.mergeSort leU)`: `ImplementsMapped` is
  `Implements` of `Proven/Spec.lean` (code placed anywhere, `a0..a3`, `sp`, `ra`, regions, `List UInt8`) with ONE extra
  hypothesis: the output bytes `[output.base, output.base + |x|)` are present in the memory map (`s.mem[_]?` is
  `some`). `sortProg` uses no stack and never touches the scratch region.
- Axioms: the same list as `compile_ok`. Check times: `SortIns` 1.9 s, `SortMachine` 1.3 s.
- Tested: `asm/arr_test.py sort 300`: QEMU == Sail C emulator == Python `sorted`, guards and input intact.
- The old `Proven/Sort.lean` (`sort_ok` with `sorry`, hand-written merge sort `asm/sort.S`) and
  `Proven/SortSteps.lean` are superseded and remain unproved.

## Layout

- `Proven/Spec.lean` — the specification (`Cfg`, `Retires`, `runsTo`, `Implements`, ...). Read this first.
- `Proven/SailEval.lean` — `sail_eval`, a call-by-value symbolic executor tactic for Sail models.
- `Proven/Regs.lean`, `Proven/Step.lean` — register facts and per-instruction step lemmas for `try_step`.
- `Proven/Code.lean` — source language `Exp` and the RV64I code generator.
- `Proven/Words.lean` (generated by `Proven/gen_words.py`), `Proven/Compiler.lean`, `Proven/Reify.lean` — step
  lemmas for the emitted words, the compiler proof, and `reify%`.
- `Proven/CompilerArm.lean` — AArch64 code generator (tested, not proved).
- `asm/` — RV64I merge sort, QEMU vs Sail C emulator co-simulation (`cosim.py`), compiler test.
- `asm-arm/` — AArch64 merge sort and QEMU harness.
- `arm-gen/` — `regen.sh` regenerates the ARM Lean model from pinned upstream commits; `DIFFS.md` lists every
  diff from upstream.
- `armv9-lean/` — generated ARM v9.4-A Lean model (do not edit by hand).
