# nano MVP: Int64 + the end-to-end chain (branch nano-mvp)

Setup: nano-mvp = origin/nano-proof + origin/nano-e2e + origin/main. nano-proof had already merged nano-e2e and
taken the name `nanoGen` for the proved IR-based generator (`Nano/GenIr.lean`); nano-e2e's stack generator is
`nanoGenS`/`nanoCompileS` (`Nano/Gen.lean`). Decision: keep nano-proof's names (not `nanoGenIR`), they are already on
both branches' history.

## Int64
Decisions:
* An `Int64` program elaborates to the SAME `Prog`/`Ex` as a `UInt64` one: numerals as their two's complement bits
  (mod 2^64, as Lean's `OfNat Int64`), `-n` as `Ex.num (0 - n)` (Lean: `Neg.neg (OfNat.ofNat n)`). `+ - *` on Int64 are
  the UInt64 operations on the bits, so the code generators and their proofs need NO change (`Nano/Int.lean`:
  `denI_toUInt64`, `evalI_eq`, `nanoRun_int`).
* `nanoElabT : List UInt8 → Option (Bool × Prog)` also returns the type (`true` = Int64); `nanoElab = (·.2) <$> nanoElabT`.
  Every type token of a program must be the same (`uniTy`), else `none` (Lean rejects mixed programs too).
* Negative numerals: `-n` (also `- n`) accepted exactly where an operand of `+ - *` / a let value / a parenthesised
  expression starts (parser `pApp`); NOT as a bare function argument (`g -5` is binary minus in Lean, nano rejects;
  write `g (-5)`). `-x` and `-(e)` are not nano (Lean accepts; nano rejects). `--` is rejected by the lexer (a Lean
  comment). Also allowed for UInt64 (Lean has `Neg UInt64`, same bits).
* Meaning: `Prog.evalI` / `denI` with Lean's `Int64` `+ - *` (wrap), numerals `UInt64.toInt64`.
  Bytes: each argument and the result as 8-byte little-endian two's complement (`encI`, `encIs`).

Evidence:
* `Nano/AgreeInt.lean` (generated by `Testing/nano/gen_agree_int.py`, corpus `INT_CORPUS` in nanolib.py): 22 Int64
  programs, per program `elabEq` (`decide +kernel`), `agree` (∀ Int64 inputs, by `rfl`: nano = Lean's own `def`),
  `run` (∀ inputs, `nanoRun P (encIs args) = some (encI (f args))`).
* `Testing/nano/fuzz_int.py 250 11 60`: 250 random Int64 + 60 random UInt64 programs with negative numerals, 8 signed /
  edge input vectors each (2480), 0 mismatches vs Lean's real defs run by the interpreter; 6 negatives rejected
  by nanoElab (Lean rejects 3; accepts `x --5` (comment), `-x`, `x * - - 5`: nano is a strict subset there).
* Machine tests, proved generator `nanoGen` (IR route): `python3 Testing/asm/nano_int_test.py 12 5`: 22 corpus + 12
  random Int64 programs × 8 signed/overflow/edge inputs = **272 pairs**, QEMU == Sail == expected at `memoryNeeded`,
  OOM flag at `memoryNeeded - 1`, writes only in output + work; the emitter also checks expected (`nanoRun`) ==
  `encI` of Lean's own `def` and words == `nanoGen p`.
* Machine tests, stack generator `nanoGenS` (nano-e2e): `NANO_INT=1 python3 Testing/nano/nano_test.py 30 3`:
  22 + 30 Int64 programs × 6 inputs = **312 pairs** on qemu-riscv64 and Sail == `Prog.eval` (sp restored).
  (UInt64 run unchanged: `nano_test.py 5`: 264 pairs.)
