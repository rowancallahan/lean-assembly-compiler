# SURVEY-S1: Sail RISC-V Lean model + Spec/Compiler on Lean 4.35.0

Status: **PARTIAL**. The Sail model does not build as-is on 4.35.0; three independent breaks found.
With survey-only patches for all three (one of them stubs a model function, one drops code generation
for `instruction`) the model builds and **all 11 Spec modules build unchanged**. Compiler got one
first-pass `lake build Compiler` (115 s): 6 modules fail directly, the rest of the graph behind them is unbuilt.

Setup: repo @ab0e3c5f (nano-v2-src), scratch copy; `sail-riscv-lean` from `build-cache`
(opencompl @51c635c, lean-sail v5 @0794631, built for 4.29.0); Lean 4.35.0 (commit eb6cafb7) from the
GitHub release tarball. 4 cores, 15 GB. No `/usr/bin/time`; wall/RSS from `getrusage(RUSAGE_CHILDREN)`
plus `free` sampling every 2 s.

## Break 1: constructor tag limit (Defs.lean)

`inductive instruction` has 353 constructors. `LeanMaxCtorTag` is 243; 4.35 checks this in
`CtorInfo.checkValid` (`Lean/Compiler/LCNF/Basic.lean:163`) when the inductive is compiled, which the
inductive elaborator now does unconditionally (`Lean.compileDecls` in `Elab/MutualInductive.lean:1575`).
On 4.29 it was not checked. Result: 1 "tag too big" + 353 `dependsOnNoncomputable` errors from the
derived instances at line 751, and the same for `ExecutionResult` (1552) and `Step` (1606) which contain
`instruction`. The file is already inside `noncomputable section`, and inductives cannot be marked
`noncomputable`, so there is no source-level modifier that fixes it.

Survey-only patch (not a real fix): a local command wrapper that elaborates the inductive and then
discards the messages and async report tasks, applied to those three inductives:

    open Lean Elab Command in
    elab "nocodegen " c:command : command => do
      let m := (← get).messages
      elabCommand c
      modify ({ · with messages := m, snapshotTasks := #[] })

With it `Defs` builds (38 s vs 20 s on 4.29). The types exist in the kernel, but have no compiled code,
and the derived `BEq/Repr/Inhabited` instances have no code either. Impact on this repo was not measured.
`native_decide`/`#eval` appear in only 3 places under Spec/Compiler/Riscv (`Compiler/Front/PipeFront.lean`,
`Riscv/Steps/Branch.lean`); whether they touch `instruction` is unchecked.

Real fix options: regenerate with a Sail Lean backend that splits the `instruction` union (≤244 ref
constructors per type), or stay on the last toolchain without the check. Which toolchain between 4.30
and 4.34 introduced the check was not bisected.

## Break 2: `assert` is now a `do` element

4.35 has an experimental `assert` do-element (warning text: "The `assert` element is part of the
experimental intrinsic verification syntax"). The generated model calls its own
`LeanRV64D.assert (p : Bool) (s : String) : SailM Unit` as a do statement 1255 times, e.g.
`assert false "Pattern match failure at unknown location"`. These now parse as the new element:
368 reported errors over 28 modules (capped at 100 per file).

Patch: mechanical, `sed -E 's/^(\s*)assert /\1LeanRV64D.assert /'` over `LeanRV64D/*.lean`
(1255 lines), plus one `then assert` in `Step.lean:449` (a `then` branch inside `do` is also a do element).
After it, all those modules build.
The elaborated term is the same constant as before only where `assert` previously resolved to
`LeanRV64D.assert` rather than `PreSail.assert`; not verified per file.

## Break 3: `RvfiDii.lean` does not terminate

2.1 s on 4.29. On 4.35: killed after 549 s at 4.7 GB RSS, single thread. Culprit is
`print_rvfi_exec` (lines 1187–1224): one `do` block of 18 statements of the form
`(pure (print_bits "..." (_get_..._field (← readReg r))))`. Confirmed by stubbing: replacing only that
body with `pure ()` makes the module build in 2.7 s; stubbing `rvfi_write`/`rvfi_read` instead does not
help. Root cause inside Lean (do-elaborator vs. nested `←` lifts, or something else) not diagnosed.
The stub changes the model's definition of a debug-print function; nothing in Spec noticed.
