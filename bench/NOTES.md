# Instruction counts: our generated code vs C (branch `bench`, pinned to main 9310b1a)

Everything here was measured; files: `bench/bench.c` (natural C versions), `bench/bench.py` (harness), `bench/emit_exp.lean` (expression words),
`bench/leanbench.lean`, `bench/results/` (raw `results.json`, `tables.md`, disassemblies). Reproduce: `python3 bench/bench.py [FUNC...]`.

## Method
- Same driver for all variants: loads `a0..a3`/`x0..x3` and `sp` from a table, calls `bench_fn`, stores counts. Same random bytes (seed 1) for every variant of a function; every run's output (and returned value) is checked against a Python model (0 wrong).
- **RV64:** `csrr minstret` before/after the call under `qemu-system-riscv64 -icount shift=0` (as `asm/msort_test.py bench`). **AArch64:** PMU `INST_RETIRED` (`pmevcntr0_el0`, event 0x08; enabled by `pmcr/pmcntenset/pmevtyper0`) under `qemu-system-aarch64 -cpu cortex-a72 -icount shift=0`; checked on a 1000-iteration loop (2002 counted for 2000+2 instructions).
- An empty `ret` function is measured per ISA and subtracted: counts are instructions executed inside the function incl. its final `ret`.
- C: `riscv64-linux-gnu-gcc -march=rv64i -mabi=lp64 -O0/-O2/-O3` and `aarch64-linux-gnu-gcc -O2`, all with `-ffreestanding -nostdlib -fno-tree-loop-distribute-patterns` (no memcpy/memset calls). Sorts: stable bottom-up merge sort (`ms_buf`) and insertion sort on bytes; others simple loops. `-O3` on rv64i vectorizes byte copies into 8-byte `ld/sd` loops (take/inc), which is why `take`/`inc` are so low there.
- "hand" = `asm/sort.S` (RV64) and `asm-arm/sort.S` (AArch64), called directly.
- n = 100, 1000, 100000 (insertion sort: 100, 1000, 10000, it is O(n^2)).

## Where our merge sort's instructions go
Ours: 79 instructions per inner-loop iteration (`0x364..0x49c` in `bench/results/ours_msort.dis`; the loop of `innerM` in `Proven/SortMergeSrc.lean`; one iteration = one output byte of one pass; 1394/elt at n=1e5 = 17 passes x ~82). gcc -O2: ~11 on the common path (`bench/results/gcc_O2_ms_buf.dis` `.L37`: 2 address adds, 2 `lbu`, `bgeu`, `addi`, `addi`, `add`, `sb`, 2 loop branches); hand-written `asm/sort.S`: ~16.

| category of the 79 | instructions | share | what it is |
|---|---|---|---|
| register moves through temporaries (`add rd,x0,rs`) | 23 | 29% | every variable read copies the register into `t0/t1/..` first (`gen (.var i) = add t,x0,a`) |
| actual ALU ops (`sltu/and/xor/add`, incl. the 3 address adds and index updates) | 16 | 20% | inherent, roughly what gcc also does |
| branch-free select (`snez;neg;xor;and;xor`) x3 | 15 | 19% | `ite` for `x`, `y`, and the stored byte; gcc uses branches/loads instead |
| spill-slot `ld/sd` (`x3`-relative frame) | 11 | 14% | 7 spill slots for `x, y, mid, e, i, w, ww`: the program has more variables than registers; 8 loads + 3 stores per iteration |
| constant `1` built by `li;slli;addi` (x3) | 9 | 11% | `t ^ 1`, `k + 1`, `q + 1`: constant 1 costs 3 words |
| byte data `lbu/lbu/sb` | 3 | 4% | inherent |
| loop control (`beqz` + `j`) | 2 | 3% | inherent (gcc fuses to 1) |

So ~49 of 79 (62%) are overhead of the code generator itself (moves, constants, select slack), 11 more are spills. The in-order list of what matters most:
1. **Operands in place / no copy through temporaries** (23 insns, 29%): use `a_i`/slot registers directly as operands and write results to their destination register. Already implemented and measured as the "fast" backend on `speed` (it removes all `move` words in the expression corpus).
2. **Constants** (9 insns, 11%): a single `addi t,x0,c` or an immediate-form op (`xori t,t,1`, `addi k,k,1` is then 0 extra words). Done in the fast backend.
3. **Register allocation instead of spill slots** (11, 14%): 8 live variables + temporaries exceed the 11 temporaries only because variables live in `a`/slots and the allocator does not reuse registers; keeping `x,y,mid,e` in registers removes 8 `ld` and 3 `sd`. Needs a new proof piece (frame reads/writes become register ops).
4. **Select** (15, 19%): `ite c a b` with a 0/1 condition needs 4 instead of 5 words (drop `snez`: saves 3); `x = src[p<mid ? p : k]` patterns are cheaper as a branch (needs branch support inside expressions, i.e. a proof change); the final `if t then x else y` of the store could be `sb` of a selected value by a short forward branch.
5. **Loop shape** (2-3 insns): bottom-tested loops (one branch per iteration) and hoisting the loop-invariant `min(...)` computations; small.
Estimate (not measured): steps 1+2+select-slack remove ~35 of 79; with step 3 ~24; the remaining gap to gcc's ~11 is the branch-free merge (gcc uses data-dependent branches).
For the simple loops the same: `sum` 20 vs 4 per byte (5x), `take` 21 vs 5, `inc` 25 vs 6: each is the loop body `lbu; load/store of slots; moves; constant 1 (3 words); add; compare; branch`.

Lean's list mergeSort on x86 costs about as much as our proved sort per element (it allocates lists), ~12x more than C.

## Caveats
- QEMU `-icount` counts retired instructions of QEMU's model, not cycles; branch-free vs branchy code has very different cycle costs, which this table ignores.
- gcc -O3 `take`/`inc` use unaligned-safe word copies only for large n (n=100: 1.0/elt).
- Random bytes only (one input per size); merge-sort counts are data-dependent by a few percent.
- The pipe `sort`-based entries at n=100000 took 27 s of QEMU time each (1.07e11 instructions).
